# DailyBrain

Android-приложение для ежедневных упражнений на память, внимание и арифметику. Помимо локальной истории и статистики, текущая ветка включает серии тренировок, систему XP и эндорфинов с историей операций, достижения, локальную ленту событий и синхронизацию ленты через Firebase для подключённых профилей.

> Документ описывает актуальную реализацию ветки `version_2_singl_module_multi_users` и последующие изменения магазина/подарков. При изменении реализации обновляйте соответствующие разделы README.

## Возможности

### Тренировки

| Тренировка | Реализация и результат |
|---|---|
| Арифметика | Генерирует примеры на сложение, вычитание и умножение. По завершении показывает результат и разбор ответов; сохраняет длительность, точность, количество заданий и правильных ответов. Текущий дефолт запуска во ViewModel — 50 заданий. |
| Запоминание слов | Загружает слова из `app/src/main/assets/memory_words.json`, выбирает 30 уникальных слов, показывает их для запоминания до 120 секунд и переходит к вводу воспроизведённых слов. Переход к вводу можно выполнить раньше. Проверка ответов нечувствительна к регистру и крайним пробелам; результат включает пропуски, ошибочные и повторные ответы. |
| Тест Струпа | Показывает набор из 40 слов-названий цветов, где нужно воспринимать цвет шрифта, а не смысл слова. Используются красный, синий, жёлтый и зелёный цвета; по умолчанию около 20% стимулов конгруэнтны. Сохраняется время выполнения. |
| Тренировка счёта | Экран с инструкцией и таймером; пользователь завершает занятие вручную. Сохраняется длительность. |

Таймеры активного времени используют `ActiveTimeTracker`: интервалы, когда приложение находится в фоне или тренировка приостановлена, не должны добавляться к длительности. Время тренировки считается по монотонным часам, а календарные отметки и время начала/окончания сохраняются отдельно.

**Важная семантика результатов:** для Струпа и тренировки счёта сейчас записываются нулевые `taskCount`, `correctCount` и `accuracyPercent`; для них достоверная основная метрика — длительность. Не интерпретируйте эти поля как измеренную точность. Для арифметики и словесной памяти количество задач и правильных ответов имеет смысл.

### Главный экран и история

- В верхней строке главного экрана отображаются непрерывная серия дней, баланс XP и баланс эндорфинов.
- Основная недельная карта показывает отдельные дни для арифметики и отдельные индикаторы памяти, теста Струпа и устного счёта. Выполнение дополнительного упражнения не отмечает арифметику выполненной.
- Кнопки дополнительных упражнений показывают выполнение своего типа в текущей ISO-неделе (с понедельника по воскресенье).
- Арифметические дни окрашиваются по факту завершения именно арифметики: оранжевый — выполнена, синий — пропущенный день после первой тренировки, серый — даты до самой первой тренировки и текущий/будущий день без результата. До загрузки истории из Room прошедшие и текущий дни также остаются серыми, чтобы не показывать ложные пропуски.
- Непрерывная серия дней учитывает любое завершённое упражнение — арифметику, память, тест Струпа или устный счёт. Она строится по локальным календарным датам завершённых сессий; `training_days` остаётся индексом активности для календаря.
- Календарь истории позволяет переходить между месяцами и открывать выбранную дату.
- Экран истории за день показывает занятия, время окончания, длительность и, где это применимо, точность и правильные ответы. Запись можно удалить после подтверждения.
- Удаление занятия пересчитывает календарные дни, связанные агрегаты статистики, награды и лучшие результаты за затронутую дату.

### Исправления после проверки сборки и цифровой клавиатуры

- Цифровая клавиатура арифметики приведена к компоновке из предоставленного XML-примера: три колонки, четыре ряда, крупные одинаковые клавиши; подтверждение расположено слева от нуля, удаление — справа. Клавиатура сохраняет работу в портретной и альбомной ориентациях.
- В английском ресурсе политики конфиденциальности нормализовано XML-экранирование апострофов и упрощена строка разрешений/местоположения, чтобы исключить некорректную обработку escape-последовательностей AAPT.

### Обновления интерфейса (feature/visual-theme-navigation-polish)

- Нижняя навигация показывает пять иконок без видимых подписей; доступные названия разделов остаются в accessibility-описаниях.
- На главном экране ободок дневной кнопки арифметики уменьшен; анимация нажатия использует смещение вниз и пружинное возвращение. Подпись дня недели расположена справа от кнопки и использует контрастный цвет темы/динамического фона.
- Периоды графика статистики отображаются компактно: «д», «н», «м», «6м», «г», «все».
- Экран правил Струпа содержит пример из четырёх цветных карточек с правильными ответами. Кнопка информации в верхней панели открывает полное вступление к упражнению.
- Экран политики конфиденциальности доступен из настроек профиля, содержит разделы о локальных данных, Firebase/Google, разрешениях, хранении и безопасности; закрывается крестиком в верхней панели.
- Экран арифметики уже адаптирует раскладку для альбомной ориентации: условие и прогресс находятся слева, цифровая клавиатура — справа.

### Статистика

Экран статистики содержит вкладки общей статистики, арифметики, памяти, счёта и теста Струпа. Для отдельных тренировок доступен график по периодам: неделя, месяц, полгода, год и всё время. Показатели включают количество тренировок, занятий за последние 7 дней, суммарную/среднюю длительность, точность там, где она измеряется, серии дней и рекорды.

- Для арифметики лучшее время учитывается только при точности не ниже **95%**.
- Для памяти сохраняется рекорд количества правильно воспроизведённых слов.
- Для Струпа и счёта рекорд — минимальное время.
- Правило порога для арифметики находится в `core/database/StatisticsRules.kt`.

### Профили и аватар

- Поддерживаются несколько **локальных** профилей: создание, переключение, редактирование и удаление активного профиля.
- Профиль хранит отображаемое имя, автоматически сгенерированный псевдоним, пол (если задан), дату рождения, страну, город и временные метки.
- Удалить единственный оставшийся профиль нельзя. При удалении активного профиля приложение переключается на другой профиль, а тренировочная история, агрегаты, дневные рекорды и прогресс онбординга удалённого профиля очищаются.
- Редактор аватара поддерживает базовые параметры внешности, купленные костюмы и пейзажные фоны. Вкладки косметики появляются только при наличии купленных предметов; сохранение проверяет владение ими по локальному инвентарю. Публичный аватар отображает выбранные владельцем предметы без проверки инвентаря зрителя. Конфигурация хранится в JSON и версионируется через `AvatarConfiguration.CURRENT_SCHEMA_VERSION` и `AvatarJsonCodec`.
- Под кнопкой добавления друзей располагаются приватный счётчик эндорфиновых пластырей `x/5`, а ниже — горизонтальные списки полученных подарков и активных бейджиков. Блоки коллекции скрыты, пока у пользователя нет соответствующих предметов. В публичном профиле пластырь и баланс не раскрываются.
- В горизонтальных списках новые предметы находятся слева; прокрутка вправо открывает более старые. Заголовки «Подарки >» и «Бейджики >» открывают сетку из трёх столбцов. Нажатие на элемент открывает экран подробностей с крупным изображением, временем получения и информацией об отправителе или достижении.
- Изображения подарков и бейджиков в ленте открывают тот же экран подробностей. Публичная проекция коллекции хранится отдельно в `publicProfileCards/{uid}/collectibles`; блокировка в любую сторону запрещает чтение коллекции.

Поле `firebaseUid` в профиле nullable. В проекте объявлены Firebase Auth и Cloud Firestore; плагин Google Services подключается при наличии `app/google-services.json`, поэтому локальная сборка без этого файла остаётся возможной. Локальные профили без связанного Firebase UID продолжают работать с локальной историей и наградами, но не синхронизируют ленту с друзьями. Перед облачными операциями приложение проверяет, что UID авторизованного Firebase-пользователя совпадает с UID активного профиля.

### Онбординг, напоминания и системная интеграция

- При первом запуске показывается вводный экран приложения. Перед первым запуском каждого типа тренировки показываются вступление и правила; завершение хранится отдельно для каждого локального профиля.
- Локальные напоминания планируются на **18:00** и **21:00**. Уведомление показывается только если для активного профиля сегодня ещё нет записи о тренировке. После срабатывания напоминание планируется на следующий день; расписание восстанавливается при загрузке устройства и изменении времени/часового пояса.
- Иконка приложения всегда оранжевая (`brain_base`); она объявлена непосредственно на `MainActivity`, без переключаемых `activity-alias`. Состояние мозга по-прежнему зависит от тренировки за сегодня и времени суток: после 20:00 без тренировки виджет может показывать «кислое» состояние, но иконка в лаунчере не меняется.
- Для Android 13+ приложение запрашивает разрешение на уведомления. Объявлены также приём загрузки устройства, ресивер состояния мозга и App Widget.

### Визуальная система

- Светлая тема использует тёплый почти белый фон, янтарный основной акцент и сдержанные сине-зелёные вторичные цвета.
- Тёмная тема сохраняет графитовый фон `#222325`, при этом поверхности имеют несколько уровней глубины, а акцентные цвета осветлены для читаемости.
- Все базовые цвета обеих схем и семантические цвета тренировок находятся в `app/src/main/res/values/colors.xml`; компоненты получают роли из Material 3 `ColorScheme`.
- Общая геометрия интерфейса задаётся в `ui/theme/Theme.kt`, типографическая шкала — в `ui/theme/Type.kt`.
- Основные экраны переходят с плавным смещением и затуханием; обратная навигация использует зеркальное направление. Нижняя панель содержит только пять иконок (главный экран, статистика, лента, магазин, профиль), без подписей; выбранный раздел выделяется анимированным индикатором.

## Сборка и тестирование

Для сборки используется Gradle Wrapper из корня репозитория:

```bash
# Компиляция Kotlin для debug
./gradlew :app:compileDebugKotlin

# Локальные unit-тесты
./gradlew :app:testDebugUnitTest

# Debug APK
./gradlew :app:assembleDebug

# Сборка APK инструментальных тестов
./gradlew :app:assembleDebugAndroidTest

# Запуск Android instrumented-тестов на подключённом устройстве/эмуляторе
./gradlew :app:connectedDebugAndroidTest
```

Для локальной разработки используйте Android Studio с Android SDK, включающим API 37, и JDK 25 для Gradle daemon/toolchain, как указано в настройках проекта. Перед отправкой изменений минимум выполните unit-тесты и сборку debug.

### Точки входа и внедрение зависимостей

- **`DailyBrainApp`** запускает Koin, планировщик напоминаний и планировщик обновления состояния мозга. В фоновом scope инициализирует наблюдение активного профиля.
- **`MainActivity`** устанавливает splash screen, определяет стартовый маршрут через `GetStartupDestinationUseCase`, устанавливает `DailyBrainTheme` и отображает `AppNavHost`. При возвращении приложения обновляет состояние мозга.
- **`AppModule.kt`** — центральное место регистрации Room `AppDatabase`, репозиториев, use case’ов, `StringProvider` и ViewModel.
- **`StringProvider`** позволяет use case’ам/ViewModel получать локализованные Android-строки без непосредственной зависимости от UI-контекста.
- **`ActiveUserProvider`** — источник ID текущего локального профиля для data-layer. Если активный ID отсутствует, он безопасно инициализирует профиль/настройку с использованием mutex.

### Общая модель тренировок

- `ExerciseType` — перечисление типов занятий и стабильных значений для хранения: `ARITHMETIC`, `MEMORY_WORDS`, `COUNTING_TRAINING`, `STROOP_TEST`.
- `TrainingSession` — доменная модель законченной сессии: тип, время старта/завершения, длительность, точность, число задач и правильных ответов.
- `CompletedTrainingRepository` — общий контракт чтения, записи и удаления законченных занятий.
- `CompletedTrainingRepositoryImpl` записывает сессию, календарный день, общую/поточную статистику и дневные рекорды внутри Room-транзакции.
- Общие use case’ы: `SaveCompletedTrainingUseCase`, `DeleteCompletedTrainingUseCase`, `ObserveAllCompletedTrainingsUseCase`, `ObserveCompletedTrainingsByDateUseCase`, `ObserveActiveTrainingDatesUseCase`, `ObserveTrainingDaysInRangeUseCase`, `ObserveTotalTrainingCountUseCase`.

## Сохранение результата и правила статистики

`CompletedTrainingRepositoryImpl.saveCompletedTraining()` выполняет одну транзакцию Room:

1. Получает ID активного профиля через `ActiveUserProvider`.
2. Добавляет `TrainingSessionEntity`.
3. Создаёт запись календарного дня либо увеличивает `exerciseCount`.
4. Обновляет общую и статистику типа тренировки.
5. Обновляет дневной рекорд.

Ключевые правила текущей реализации:

- Дата для аналитики хранится как целое число `yyyyMMdd`; временные метки сессии — миллисекунды Unix epoch.
- ID записи сессии формируется из `startedAtEpochMs`, а не Room auto-generated ID. При изменении механизма создания сессий сохраните согласованность этой идентификации.
- Арифметический рекорд времени обновляется только при точности не ниже `StatisticsRules.ARITHMETIC_BEST_TIME_MIN_ACCURACY_PERCENT` (95%).
- Удаление занятия пересобирает `training_days`, общую статистику и статистику по упражнениям из оставшихся сессий; дневной рекорд пересчитывается для затронутой даты.
- Потоки чтения репозиториев привязаны к `ActiveUserProvider.observeUserId()`. Поэтому при переключении профиля подписки должны переключаться на данные нового профиля.

## Награды, серии и лента

### XP и правила начисления

Награды пересчитываются из сохранённой истории тренировок компонентом `feature/rewards/data/RewardRecalculator.kt`. Пересчёт вызывается при сохранении/удалении тренировки и при инициализации состояния наград профиля. Ключи наград детерминированы, поэтому повторный пересчёт не должен дублировать начисления.

| Событие | Условие | XP | Эндорфины |
|---|---|---:|---:|
| Первая арифметика за календарный день | Первая завершённая арифметическая тренировка этого дня | 50 | 0 |
| Повторная арифметика за день | Каждая следующая арифметическая тренировка в тот же день | 10 | 0 |
| Первое дополнительное упражнение типа за ISO-неделю | Первый результат каждого из типов «Память», «Струп» и «Устный счёт» в неделе | 50 | 0 |
| Недельная серия дней | Любое одно завершённое упражнение в день в течение 7 последовательных календарных дней | 100 | 10 |
| Задание недели | Арифметика минимум один раз в каждый из 7 дней ISO-недели **и** все три дополнительных упражнения в этой же неделе | 100 | 10 |
| Месячная серия | Любое одно завершённое упражнение в каждый календарный день месяца | 500 | 50 |
| Новый рекорд арифметики | После первых 7 арифметических тренировок; точность не ниже 95%; время лучше предыдущего допустимого результата; первый рекорд учитывается не раньше завершения первой недельной серии | 100 | 10 |

Дневной бонус арифметики определяется по локальной календарной дате завершения тренировки: день начинается ровно в 00:00 системного часового пояса и заканчивается перед следующим 00:00. При пересчёте наград дата вычисляется из `finishedAtEpochMs` в текущей локальной зоне, поэтому ночная и дневная тренировки одной местной даты не разделяются из-за прежнего значения поля `date`.

Выполнение памяти, Струпа или устного счёта само по себе не даёт эндорфинов. Эти упражнения могут давать XP за первое выполнение своего типа в ISO-неделе и учитываются в календарной серии дней. Дополнительные упражнения не заменяют арифметику в задании недели.

**Недельная серия и задание недели — разные достижения:**

- Недельная серия использует локальные календарные даты завершения сессий. Подходит любое из четырёх упражнений. Это скользящая серия, не привязанная к ISO-неделе: каждая седьмая подряд активная дата даёт новое достижение, пропуск календарного дня прерывает цепочку. Старт в среду означает, что первая награда будет во вторник следующей недели (среда считается первым из семи дней); переход через понедельник серию не сбрасывает.
- Задание недели привязано к ISO-неделе с понедельника по воскресенье. Арифметика должна быть выполнена в каждый из семи дней, а память, Струп и устный счёт — хотя бы по одному разу в пределах той же недели.
- Месячная серия использует те же активные календарные даты и требует тренировку в каждый день месяца. Месячные достижения имеют ключ с годом и месяцем, поэтому, например, октябрьский значок можно получить повторно в следующем году.

Арифметический рекорд — это рекорд времени, а не отдельный бейдж. Первые семь арифметических тренировок считаются тренировочными попытками; далее новый лучший результат требует точности не ниже 95% и положительной длительности. За рекорд публикуется событие в ленте, но персональный рекордный бейдж не выдаётся.

Еженедельные пороги XP в 250 и 500 отображаются событиями в ленте. Эти пороги не добавляют отдельные XP поверх уже начисленных за тренировки и достижения.

### Эндорфиновый баланс и покупки

Баланс эндорфинов рассчитывается по активным операциям в таблице `reward_ledger`; поле `endorphinBalance` в профиле хранит отображаемый текущий баланс. `EndorphinEconomy` — единый источник наград и цен:

| Предмет / операция | Цена |
|---|---:|
| Патч | 10 эндорфинов, максимум 5 патчей |
| Конфета | 10 эндорфинов |
| Кофе | 20 эндорфинов |
| Круассан | 30 эндорфинов |
| Гамбургер | 40 эндорфинов |
| Торт | 50 эндорфинов |
| Костюм | 100 эндорфинов |
| Фон (море, горы, офис или лес) | 100 эндорфинов |

Баланс и цены эндорфинов в интерфейсе сопровождаются общей фиолетовой иконкой-молекулой (`ic_endorphin_molecule`). Покупки магазина и передача подарков реализованы следующим образом:

- Списание атомарно выполняется через `EndorphinRepository.spend()`. Операция требует стабильный уникальный `transactionId`, защищена от повторного списания при retry и отклоняется, если текущего баланса недостаточно.
- Получение подарка через `receiveGift()` зачисляет стоимость подарка один раз на основе стабильного `giftId` и записывает его в локальный инвентарь `user_gifts`. Входящие подарки синхронизируются из Firestore при запуске приложения, при возвращении на экран собственного профиля и при обновлении магазина; получение создаёт событие `GIFT_RECEIVED` в ленте.
- Отозванные награды исключаются из баланса. Если ранее заработанные эндорфины уже были потрачены, баланс после отзыва может стать отрицательным; при отрицательном или недостаточном балансе новые покупки запрещены.

**Ограничение безопасности:** в конфигурации Firebase Spark без Cloud Functions Firestore Rules не могут независимо проверить локальный баланс отправителя и доказать факт списания. Правила проверяют форму документа, отправителя, получателя и допустимый тип подарка; клиентская экономика не является защищённой платёжной системой. Для строгой защиты от подделки и глобальной однократности между устройствами потребуется доверенный серверный обработчик.

### Бейджи и лента событий

За недельную серию, задание недели и месячную серию создаются записи в `user_badges`. Активные (неотозванные) бейджики и полученные подарки показываются в собственном и публичном профиле в горизонтальных списках, новые слева. Заголовок открывает отдельную сетку 3 столбца; выбор предмета открывает экран с крупным изображением, временем получения и контекстом достижения/отправителя. Для месячных бейджей используются три набора спрайтов по месяцам: `badge_months_01_04.webp`, `badge_months_05_08.webp`, `badge_months_09_12.webp`; недельные достижения используют `badge_weekly.webp`. Персональный рекорд публикуется в ленте как событие без отдельного бейджа.

Лента хранит локальные события в Room (`feed_events`) и показывает события достижений, месячных серий, получения подарков, персональных рекордов и недельных порогов XP. Порядок — от новых к старым.

- Первая страница содержит до 30 событий. Следующие страницы по 30 элементов подгружаются из локального кэша по курсору времени и ID события.
- Для профилей с подключённым Firebase UID собственные последние события синхронизируются с Cloud Firestore; публичная история ограничена последними 10 событиями на автора. События друзей загружаются из Firestore и кэшируются в Room.
- При открытии ленты запускается обновление. Общий `SaveCompletedTrainingUseCase` также запрашивает синхронизацию собственных событий после сохранения сессии. Отдельный WorkManager для этой синхронизации не используется.
- Если обновление сети завершается ошибкой, лента продолжает показывать последний успешно сохранённый кэш. Для локального профиля без Firebase UID собственные события остаются локальными, без ленты друзей.
- При расхождении истории тренировок награды и события пересчитываются; отозванные достижения помечаются, чтобы синхронизированная лента могла удалить прежнее публичное событие.

Необязательные изображения бейджей декодируются через `BitmapFactory`. Изображение бейджика или подарка в карточке ленты открывает те же подробности коллекционного предмета, что и профиль. Отсутствующий или повреждённый ресурс бейджа не должен приводить к падению всего экрана ленты.

### Главный экран: независимые статусы упражнений

Главный экран использует два разных представления:

- `completedDates` — даты любых тренировок. Они нужны для общей серии дней.
- `completedExerciseDatesByType` — даты по конкретному `ExerciseType`. По ним отмечаются отдельные упражнения, а арифметические кружки используют только даты типа `ARITHMETIC`.

Поэтому выполнение памяти, Струпа или устного счёта не окрашивает арифметический день в оранжевый. Для каждого дополнительного круга учитывается только его собственный тип упражнения за текущую неделю.

Пока Room ещё не выдал первую историю тренировок, `HomeUiState.isTrainingHistoryLoaded = false`, а прошедшие и текущий дни имеют статус `LOADING` и серый цвет. После первого значения Flow `HomeViewModel` переключает состояние в загруженное и применяются реальные статусы: выполненная арифметика — оранжевая, пропущенный прошедший день — синий, текущий день без арифметики и будущие дни — серые. Это предотвращает кратковременное отображение всех дней как пропущенных при запуске приложения.

Особенности форматов:
- `TrainingSessionEntity.date`, `TrainingDayEntity.date`, `DailyExerciseResultEntity.date` и `OverallStatisticsEntity.lastTrainingDate` — целое число `yyyyMMdd`.

### Миграции

История схемы охватывает версии 1 → 21. Помимо изменений истории, статистики, профилей, аватара и онбординга, миграция 13 → 14 добавила поля балансов/прогресса наград и таблицы `reward_ledger`, `user_badges`, `user_gifts`, `feed_events`. Миграции 14 → 15, 15 → 16, 16 → 17, 17 → 18 и 18 → 19 сбрасывают `rewardsInitialized`, чтобы при следующей инициализации пересчитать ранее начисленные награды. Миграция 17 → 18 исправляет даты начислений по времени завершения тренировки в локальном часовом поясе; миграция 18 → 19 принудительно пересобирает весь журнал наград из сохранённых тренировок, в том числе несколько недельных серий и заданий. Миграция 19 → 20 добавляет `user_inventory` и `gift_outbox`. Миграция 20 → 21 добавляет имя отправителя в `user_gifts` и метаданные отправителя в `feed_events`. Все миграции 1 → 21 зарегистрированы в Koin-модуле приложения через `Room.databaseBuilder`.

При изменении Room-сущностей:

1. Увеличьте версию `AppDatabase.version`.
2. Добавьте новую направленную миграцию в `DatabaseMigrations.kt` и зарегистрируйте её в `Room.databaseBuilder(...).addMigrations(...)` внутри `AppModule.kt`.
3. Не переписывайте старые миграции так, будто пользователи начинают с последней версии: миграция должна работать с реальной старой схемой и сохранять имеющиеся данные.
4. Проверьте изменение на существующей БД и добавьте тесты для миграции/пересчёта, если затронуты история и статистика.

В текущем коде destructive migration не регистрируется — сохраняйте это поведение, если нет отдельного явного решения терять локальные данные.

## Важные правила разработки

1. **Новый тип тренировки.** Обновите `ExerciseType` и его стабильное storage value, экран/ViewModel/use case, регистрацию DI, строки ресурсов на русском и английском, маршрутизацию, вступление/правила и флаги `OnboardingProgressEntity`, историю, статистику и соответствующие рекорды/миграции, если они нужны. Проверьте аналитику, где перечисляются все типы упражнений.
2. **Не используйте отображаемые названия для сохранения.** В БД используется значение `ExerciseType.storageValue`; отображаемое название должно идти из ресурсов.
3. **Сохранение должно быть повторяемым при ошибке UI.** Несколько ViewModel используют `pendingSession` и явный retry. При изменении сохранения не создавайте дубликаты при повторной попытке; учитывайте текущий ID сессии, основанный на времени старта.
4. **Активный профиль обязателен для запроса.** Для данных, принадлежащих пользователю, используйте `ActiveUserProvider`; не выполняйте неограниченные запросы ко всем тренировочным таблицам.
5. **Изменение критерия рекорда.** Если меняется порог 95% или формула рекордов, проверьте `StatisticsRules.kt`, обновление статистики в `CompletedTrainingRepositoryImpl.kt` и SQL backfill в `DatabaseMigrations.kt`.
6. **Таймер и lifecycle.** Тренировки, измеряющие время, должны корректно вызывать pause/resume по жизненному циклу. Для измеренной длительности используйте `ActiveTimeTracker`, а не вычисление через разницу настенных часов.
7. **Изменение аватара.** Обновляйте `AvatarConfiguration`, кодек `AvatarJsonCodec`, фабрику отрисовки/ресурсы и тесты. Для изменений формата повышайте `CURRENT_SCHEMA_VERSION` и сохраняйте обработку старых JSON.
8. **Форматы дат не смешивать.** Для истории тренировок используется целое `yyyyMMdd`; для даты рождения — ISO-строка. Epoch-время — отдельная величина.
9. **Текущая несогласованность конфигурации арифметики.** `ArithmeticTrainingConfig.DEFAULT_TASK_COUNT` задан как 100, но `ArithmeticViewModel.startTraining()` по умолчанию передаёт 50. Если меняете длительность тренировки, проверьте оба значения и тесты.
10. **Локализация.** Новые UI-строки добавляйте в `res/values/strings.xml` и `res/values-en/strings.xml`; избегайте жёстко заданного пользовательского текста в Kotlin.
11. **Не забывайте тесты.** Для бизнес-правил предпочтительны unit-тесты use case’ов/ViewModel, а для изменения БД — тесты миграции и пересчёта статистики.

## Тесты и CI

Unit-тесты покрывают типы упражнений, активный таймер, арифметическую доменную логику и ViewModel, кодек аватара, use case’ы памяти, состояние главного экрана, правила недельных достижений и цены/проверку возможности списания эндорфинов. В частности, `HomeUiStateTest` проверяет разделение арифметики и дополнительных упражнений, а также нейтральное состояние до загрузки истории; `WeeklyAchievementRulesTest` проверяет условия серии и недельного задания. Инструментальные тесты находятся в `app/src/androidTest`.

Workflow расположен в `.github/workflows/android-ci.yml`. Он собирает Kotlin, запускает unit-тесты, собирает debug APK; отдельная job собирает instrumented APK и запускает тесты на Android Emulator API 35, загружая результаты как артефакты.

Workflow запускает проверки при push в `version_1_singl_module_main_functional_local`, `codex/android-ci-emulator` и `feature/**`; pull request-триггер настроен для target-ветки `version_1_singl_module_main_functional_local`. Workflow также поддерживает ручной запуск через `workflow_dispatch`. Основная job выполняет `:app:compileDebugKotlin`, `:app:testDebugUnitTest` и `:app:assembleDebug`; отдельная job собирает instrumented APK и запускает `:app:connectedDebugAndroidTest` на Android Emulator API 35.

## История баланса XP и эндорфинов

- Нажатие на счётчик XP открывает отдельный экран истории XP; нажатие на эндорфины — самостоятельный экран истории эндорфинов. Переключателей или вкладок между балансами нет.

- Каждая операция содержит причину, локальные дату/время и, если она связана с тренировкой, название конкретного упражнения. Для личного рекорда арифметики дополнительно показывается измеренная длительность результата (например, «Новый личный рекорд в арифметике — 1 мин 15 сек»). - Для соответствия текущему балансу показываются только активные операции. Отозванные начисления с `isActive = false` исключаются.
- История обновляется автоматически через Room Flow. Причины операций локализованы на русском и английском языках.

## Удаление профиля

Удаление профиля работает по принципу **local-first** и поддерживает восстановление после отсутствия сети. Один и тот же сценарий используется на экране редактирования профиля и в списке профилей.

1. В одной транзакции Room сохраняется задача в `pending_profile_deletions` (Firebase UID, Google Subject, этап выполнения), удаляются локальная запись профиля и все принадлежащие ей тренировки, статистика, награды, инвентарь, полученные подарки и локальные события ленты.
2. Если доступна совпадающая Firebase-сессия, приложение удаляет связанные облачные данные и последним шагом удаляет пользователя из Firebase Authentication. Удаление Firebase-пользователя может потребовать недавней авторизации; при такой ошибке задача остаётся в очереди.
3. Если устройство было офлайн или Firebase потребовал повторной авторизации, при следующем явном входе через Google приложение обрабатывает задачу **до** создания облачного профиля. Старые облачные данные удаляются, старый Firebase Auth user удаляется, затем повторный вход с тем же временно хранящимся Google credential создаёт новый Firebase UID. Только после этого выполняется создание и привязка профиля.
4. После локального удаления приложение переводит пользователя на выбор профиля. Можно удалить и последний локальный профиль, а затем создать новый.

Очередь хранится в Room, версия БД — **22**. Состояние `CLOUD_CLEANUP_PENDING` означает, что облачная очистка не завершена; `CLOUD_DATA_DELETED` — облачные данные уже удалены и осталось завершить удаление Firebase Authentication. Токены Google в Room не сохраняются.

### Что удаляется и что сохраняется

Удаляются приватный и публичный документы профиля, публичная карточка и её подколлекция collectibles, резервации username/invite code, события ленты, созданные самим профилем, его входящие подарки, созданные им блокировки, а также входящие и исходящие связи подписок и обе публичные проекции этих связей.

**Отправленные подарки сохраняются.** Документы доставки в inbox других пользователей и их события получения не удаляются. Баланс эндорфинов и история получателей не меняются. Удаляются только подарки, полученные удаляемым профилем.

Документ `deletedProfiles/{uid}` создаётся **до начала облачной очистки** и сразу запрещает старому UID создавать или изменять данные, пока его токены ещё действительны. В нём есть состояние `cleanupComplete`: если приложение прервётся во время очистки, следующий вход продолжит незавершённые операции; после успешного удаления всех облачных данных состояние меняется на завершённое. Документ содержит только UID и даты, позволяет показать сообщение **«Профиль удалён»** при открытии старой ссылки. Правила разрешают старому UID только дочистить принадлежащие ему документы и завершить tombstone, но не создавать новые данные.

Firestore не удаляет подколлекции автоматически, поэтому приложение удаляет собственные подколлекции отдельными пакетами. Записи блокировок, которые создали другие пользователи в своих `blockedUsers/{otherUid}/users/{uid}`, принадлежат этим пользователям и не удаляются владельцем удалённого профиля; tombstone всё равно позволяет корректно обрабатывать старые ссылки.

### Правила Firestore

Обновлённые правила находятся в `firestore.rules`. Они позволяют участникам подписки удалять каноническую связь и её проекции, получателю удалять элементы только своего inbox подарков, а также вводят tombstone удалённого профиля и запрещают изменённому UID новые записи.

**Перед выпуском этой версии обязательно разверните правила в Firebase-проекте:**

```bash
firebase deploy --only firestore:rules
```

Cloud Functions не используются. Firebase Authentication удаляет Android-клиент после облачной очистки; операция требует недавнего входа. Сам Google-аккаунт не удаляется.
### Исправления удаления профиля и синхронизации аватара

- После подтверждения удаления с экрана редактирования используется ID профиля, зафиксированный при открытии диалога. Повторный запрос во время удаления блокируется. После локальной Room-транзакции диалог закрывается и приложение сразу открывает выбор профиля.
- Облачная очистка запускается в application scope, а не в scope экрана. Поэтому навигация не отменяет очистку; при остановке процесса незавершённая работа остаётся в `pending_profile_deletions` и восстанавливается при следующем входе через Google.
- При удалении активного профиля активный ID очищается, а `profileSelectionRequired` остаётся включённым до явного выбора или создания профиля. Удаление не переключает пользователя на соседний локальный профиль.
- Стартовый маршрут проверяет `profileSelectionRequired` до чтения пользовательского onboarding. Если приложение было закрыто на экране выбора профиля, после перезапуска оно снова открывает выбор, не зависая в ожидании активного профиля.
- `ActiveUserProvider.observeSelectedUserId()` и `UserProfileRepository.observeSelectedProfile()` передают nullable-состояние выбора. Потоки, зависящие от выбранного профиля, должны прекращать работу при `null`. Наблюдение профиля больше не создаёт отсутствующую Room-запись автоматически: первичная инициализация выполняется только при разрешённом запуске без активного профиля.
- `PublicProfileSyncViewModel` сначала получает конкретный выбранный профиль, затем подписывается на его статистику, аватар и инвентарь через `collectLatest`. Это исключает отправку аватара предыдущего локального профиля под Firebase UID следующего во время переключения.
- Экран публичного профиля получает конфигурацию аватара из `publicProfileCards/{targetUid}` — той же адресной карточки, которая используется в списке друзей. UID целевого пользователя не подменяется UID просматривающего.

- Основной зелёный цвет действий — `#41BA46`: добавление друзей, сохранение профиля, покупка и отправка подарков.

## Подарки костюмов и фонов, настройки профиля

- Настройки тёмной темы и динамического фона хранятся отдельно по `localAccountId`. При переключении локального профиля его настройки восстанавливаются; для существующего профиля прежние общие настройки переносятся один раз.
- Динамический фон главного экрана меняет оранжевую окраску только для дней текущей недели, в которые завершена арифметическая тренировка. При отсутствии завершённой арифметики фон остаётся обычным цветом активной темы.
- В карточках костюмов и фонов доступна отправка подарка подписчику. Эндорфины списываются локально, а доставка идёт через существующую Firestore-очередь с уникальным ID подарка; получатель получает предмет в локальный инвентарь.
- Лента показывает отправленные и полученные обычные подарки, костюмы и фоны. Новость получателя публикуется после локального зачисления/добавления предмета, новость отправителя — после успешной записи доставки в Firestore.
- Правила Firestore расширены для новых типов feed-событий и проверки разрешённых ID косметики и её цены.

- Кнопки перехода к выполнению упражнения на экранах правил, полной информации и календаря, а также кнопки завершения на экранах результатов упражнений используют единый зелёный цвет действий.
- Цена костюма или фона отображается и тогда, когда предмет уже есть в инвентаре: его по-прежнему можно подарить другому пользователю, а стоимость отправки видна заранее.
